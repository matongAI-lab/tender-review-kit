# 技术线 · ▲★ 实质性响应（专项工作指南）

## 你的任务

处理招标文件技术规范里的 ▲/★ 标识参数，产出**两样**：
1. **技术响应废标** —— 落在「实质性要求」范围内的 ▲ 不响应 = 否决
2. **全量 ▲★ 参数清单** —— 每条逐行列出，给投标人/审核员逐条核对响应

你只列事实，不下「投/不投」结论。

## 输入

- `<项目>.lines.txt` — 带行号全文（事实来源，引用必带行号）
- `<项目>.hits.json` — 撒网结果，`hits.emphasis_marks` 是 ▲/★ 命中底稿（行号 + 拆分片段）。注意：它是线索池，不替代回到 lines.txt/原表格逐条核对。

## 关键判断（务必先做）：定位「实质性要求」范围

⚠️ **货物类标书 ▲ 通常极多(实战见过 300+ 的),但绝大多数是评分项(满足得分/不满足扣分),不是否决项。**

**第一步**：在 lines.txt 里找「实质性要求和条件」到底明确列了哪几项
(实战中见过全文只锁 2 项的极端情况:最高限价 + 质量保证期 —— 整本 300+ 个 ▲ 都不是否决而是评分)。
- 落在实质性要求范围内的 ▲ → **技术废标**（不响应即否决）
- 其余所有 ▲ → **全量参数清单**（评分/响应项，漏一条可能丢分，但不出局）

**找不到明确的实质性要求范围 = 危险信号**，在工作区注明「未定位到实质性要求范围，▲ 性质待人工确认」，不要默认全部当废标（虚增）或全部当评分（漏判）。

## 步骤

1. 定位实质性要求范围（在 lines.txt 里找「实质性要求和条件」的明确列项）。
2. 从 `hits.json` 的 `emphasis_marks` 取**全部** ▲/★ 命中（行号 + 拆分片段）——这是全量底稿；如同一行仍含多个标识/多个参数，必须继续拆。
3. 按行号 Read lines.txt 的**局部**核对参数细节。Word 表格常被摊平成一条超长行，必须按 `▲/★/※ + 编号/参数名` 逐项切开，不能把一行当一条。
4. 分两类：实质性要求内 → 技术废标；其余 → ▲ 参数清单。

## 输出（写入工作区 `workspace/<项目>.工作区.md` 两个 section）

**`## 技术线·废标`**（实质性要求内的 ▲）
```
| ID | 类别 | 废标条款 | 出处(行号) | 必须材料 | 核实步骤 |
```
类别 = `技术实质性响应`；ID = `T-D001` 起。

**`## 技术线·▲★标识参数`**（全量，每个 ▲ 一行）
```
| ID | 标识 | 参数 | 出处(行号) | 需提供证明 | 我方响应 |
```
ID = `T-E001` 起；「我方响应」列留空给投标人填。

## 铁律

- **全量不压缩** —— ▲ 参数清单条数应 **≥ 撒网命中数**（完整性护栏查 ≥80%）。撒网 331 个就列 331 个，**不许摘要成"主要几项"**。这是本项目最痛的教训。
- **长表格行继续拆分** —— 如果一个 lines.txt 行里有多个 `▲/★/※` 或多个参数编号，必须逐条列；`hits.json` 只能作为底稿，不是最终清单。
- **排除说明性噪音** —— `※注意`、格式说明、页眉页脚、目录页、评分说明中非参数性提示不进 `技术线·▲★标识参数` 主清单；需要交代时写在处置台账。
- **维度不绑值** —— 列「要求 HDMI 输出 ≥1 路」这种参数本身，照原文。
- **只列事实** —— 列参数 + 出处，不评"我方能不能满足"。

## 返回（不返回完整清单，已写文件）

只返回摘要：技术废标 N 条 + ▲ 参数清单 M 条（对比撒网命中数）+ 定位到的实质性要求范围是什么 + 1-2 条流程改进建议。
